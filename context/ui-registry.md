# UI Registry

Living document. Updated after every component is built. Read this before building any new component — match existing patterns exactly before inventing new ones.

---

## How to Use

Before building any new component:

1. Check if a similar component already exists in this registry
2. If yes — import and use it. Match its exact class structure if extending
3. If no — build it following `ui-rules.md` and `ui-tokens.md`, then add it here

After building any component — add it to this file with:

- Component name
- File path
- What it does
- Key classes or patterns used

This prevents duplicate components and keeps the UI consistent as the codebase grows.

## Providers

- **`ThemeProvider`** — `src/components/providers/ThemeProvider.tsx`. Client component wrapping the app in root layout. Reads/writes the `dark` class on `<html>` and the `theme` localStorage key. Built on `useSyncExternalStore` (not `useState` + `useEffect`) so the client snapshot can differ from the server snapshot (always `"light"`) without a hydration mismatch — the anti-FOUC inline script in `layout.tsx` (via `next/script`, `strategy="beforeInteractive"`) applies the real class before hydration, and a `MutationObserver` in the provider's `subscribe` picks up both that and system-preference changes. Exposes `{ theme, setTheme, toggleTheme }` via context.
- Public hook: `src/hooks/useTheme.ts` — re-exports the provider's context hook as `useTheme()`. Use this from components; don't import `ThemeProvider`'s internals directly.
- Public hook: `src/hooks/useUser.ts` (Feature 17) — wraps `authClient.useSession()` from `better-auth/react`, returns `{ user: SessionUser | null, isLoading: boolean }`. Exports `SessionUser = { id: string; name: string | null; email: string; image?: string | null }`. `"use client"` only. Accepts an optional `initialUser?: SessionUser | null` — when a server layout passes it (via `auth.api.getSession({ headers: await headers() })`), `isLoading` is permanently `false` from the first render so the correct auth state paints immediately with no pop-in delay. When `initialUser` is `undefined` (not passed), `isLoading` mirrors `authClient.useSession()`'s `isPending` (original behavior). **Pattern: server layouts call `auth.api.getSession()` in a try/catch and pass `session?.user ?? null` as `initialUser` to the navbar component; the navbar forwards it to `useUser()`.** Gate auth-dependent UI on `!isLoading && user`.

### Navbar

File: `src/components/layout/Navbar.tsx`
Last updated: 2026-06-24 (Feature 17 — added logged-in state)

| Property         | Class                                                                 |
| ---------------- | ---------------------------------------------------------------------- |
| Background       | Header: `bg-surface dark:bg-background`. Pill: always `bg-surface` (both themes) |
| Border            | Pill only: `border-border-light` — header itself has no border          |
| Border radius     | Pill container: `rounded-xl`. Active/inactive nav link: `rounded-xl`. Follow-on-X pill, Log In, hamburger: `rounded-lg` |
| Text — primary    | `text-text-primary` — logo, nav link text/icons, "Follow on" text       |
| Text — secondary  | `text-text-secondary` — hamburger icon default state                   |
| Spacing           | Pill: `px-1.5 py-3.5`. Nav link: `px-3.5 py-1.5 gap-1.5`. Follow-on-X: `px-3.5 py-2 gap-1.5`. Logo: `gap-2` |
| Hover state       | `hover:bg-surface-secondary` — inactive nav links, Follow-on-X, hamburger |
| Shadow            | `shadow-xl` — pill only; header carries no shadow                       |
| Accent usage      | `bg-accent-muted text-accent` — active nav link fill only               |

**Pattern notes:**
The header itself has zero chrome (no background distinct from the page, no border, no shadow) — only the floating pill underneath has its own surface/border/shadow. This matches `designs/hero-section-1-event-loop.png`, where pixel-sampling showed the entire light-mode canvas is pure white (`bg-surface`), not the off-white `--color-background` token. In dark mode the header (and `body`, and `Footer`) deliberately switch to `dark:bg-background` instead, diverging from the pill's `bg-surface` — dark themes need a darker backdrop than their elevated surfaces for the pill to read as distinct, since `shadow-xl` barely registers against a dark background. Active nav state uses a pale accent fill (`bg-accent-muted text-accent`), never an underline — a white/transparent active segment would be invisible against the white pill. Any new "floating pill on a flat backdrop" component should reuse this exact `bg-surface`/`dark:bg-background` split, not invent a new one.

**Responsive breakpoint (Feature 09 audit, corrected again same feature):** the full desktop nav (pill + Follow-on-X/theme-toggle/Log-In group) and the hamburger toggle/menu switch on `lg:` (1024px), **not** `xl:` (1280px) — an earlier pass raised this to `xl:` after measuring a 70px overflow at exactly 1024px with full-size elements, but hiding the real nav behind a hamburger through the whole 1024–1279px tablet-landscape range was explicitly rejected. The actual fix is to keep the `lg:` switch and compact what renders there instead: pill links `px-2 py-1.5 text-xs gap-1` (icon `size-3`), "Follow on X" goes icon-only with `aria-label="Follow Frontend Forever on X"` (visible text in `hidden xl:inline`), Log In `px-3 py-2 text-sm`, logo `text-4xl`, wordmark hidden only in the 1024–1099px band (`min-[1024px]:hidden min-[1100px]:inline` — both bounds must be arbitrary values, a named breakpoint like `lg:hidden` does not cascade correctly alongside an arbitrary one). `xl:` (1280px) overrides restore full roomy sizing. Verified zero overflow/clipping at 1024/1100/1279/1280px via screenshots.

**Feature 17 update — logged-in state:** Navbar accepts `initialUser?: SessionUser | null` prop, forwarded to `useUser()`. `(main)/layout.tsx` is now `async` — it calls `auth.api.getSession()` server-side and passes the result so the correct state paints on the first render. Follow on X and `ThemeToggle` are **always rendered** (unconditional) — pulling them outside the auth branch prevents any flash on refresh. Only the last slot changes: `{!isLoading && (user ? <UserDropdown /> : <Link>Log In</Link>)}` — nothing renders there while `isLoading` is true, so there is no swap from Log In → avatar. Mobile menu follows the same pattern. The pill layout, breakpoints, and all existing class structure are unchanged.

## Shared UI Components

- **`ThemeToggle`** — `src/components/shared/ThemeToggle.tsx`. Icon-only button (`Sun`/`Moon` from `lucide-react`) calling `useTheme().toggleTheme()`. Styled with `bg-surface border-border` + hover `bg-surface-secondary`, 36px (`size-9`) square, `rounded-lg`. Has `aria-label` describing the action it performs (not the current state).
- **`XLogo`** — `src/components/shared/XLogo.tsx`. Inline SVG of the X (formerly Twitter) brand glyph — lucide-react ships no brand icons in this project's pinned version, so the official logo path is inlined. `fill="currentColor"` + `aria-hidden`, defaults to `size-4`, accepts a `className` override. Use this anywhere the X brand mark is needed (Navbar "Follow on X", Footer social row) instead of lucide's `X`/`XIcon` (which is a generic close ✕, not the brand mark).
- **`Markdown`** — `src/components/shared/Markdown.tsx` (Feature 25, promoted from `features/practice/ChallengeDescription`). `{ markdown }`. A dependency-free Markdown-subset renderer: h2/h3 headings, paragraphs, **ordered (`1.`) and unordered (`-`/`*`) lists**, ``` fenced code, `>` blockquote, inline `code`, `**bold**`, `*italic*`. Token-styled, authored content only (no HTML-injection surface). Shared by challenge descriptions (`features/practice`) and interview answers (`features/interview-prep`) — the rule-of-three promotion. Ordered-list support was added here (the original renderer only did bullets); any new consumer authoring numbered steps depends on it.
- **`UserDropdown`** — `src/components/shared/UserDropdown.tsx` (Feature 17). Avatar button + dropdown menu shared by both `Navbar` and `AppNavbar`. Props: `user: DropdownUser` (`{ name: string | null; email: string; image?: string | null }`). Renders a `size-8` `Avatar` as the trigger (initials fallback: first letters of name words, or first letter of email). Dropdown items: Profile → `/settings/profile`, Settings → `/settings`, theme toggle (calls `useTheme().toggleTheme()`), Sign Out. **Critical: uses `@base-ui/react/menu` via `dropdown-menu.tsx` — `DropdownMenuTrigger` has no `asChild` prop; place the `<Avatar>` directly as its child, never wrap with a `<button>` or use `asChild`.** Trigger styled with `rounded-full ring-offset-background hover:ring-2 hover:ring-border focus-visible:ring-2 focus-visible:ring-accent disabled:pointer-events-none` — no separate button element. **Sign Out loading state:** `isSigningOut` state lives in `UserDropdown`, not inside the menu item. When `isSigningOut` is true, the trigger avatar fades to `opacity-30` and a centered `Loader2 animate-spin` overlays it — this is always visible in the navbar even after the dropdown closes. The Sign Out item uses `variant="destructive"` + `className="text-error focus:bg-error-muted focus:text-error [&_svg]:!text-error"` — the `variant` exempts it from `DropdownMenuItem`'s base `not-data-[variant=destructive]:focus:**:text-accent-foreground` rule (which would otherwise override the icon's inherited color and make it invisible on hover), and `[&_svg]:!text-error` pins the icon color with `!important` against any remaining descendant selector from the destructive variant's own SVG-color rule.

Folder: `src/components/shared/simulator-chrome/` — `BrowserChromeBar.tsx`, `PanelHeader.tsx`, `SimulatorControls.tsx`, `ScenarioSwitcher.tsx` (Feature 23), `types.ts` (`SimulatorSpeed = 0.5 | 1 | 1.5 | 2`, plus `SimulatorRootProps` + `ScenarioOption`, both Feature 23). Play/Pause, Step, Step Back (disabled at frame 1), Step forward (disabled at last frame), Restart, Autoplay `Switch`, Speed `DropdownMenu` (0.5/1/1.5/2x). **Visible and tappable on mobile by default** — see `ui-rules.md` → Responsive Design; this flipped from "hidden by default" to "shown by default" once Feature 10 confirmed Feature 09's CodeRabbit-driven exception as the standing pattern, not a one-off.
- `useSafeReducedMotion` — `useSyncExternalStore`-based `prefers-reduced-motion` check (server snapshot always `false`, avoids the hydration-mismatch bug documented under `EventLoopSimulator` below). Any component in any simulator that needs to check reduced motion should import this rather than calling Framer Motion's `useReducedMotion()` directly.
- **`ScenarioSwitcher`** (Feature 23) — `{ scenarios: ScenarioOption[], activeId: string, onChange: (id) => void }`. Pill-group selector shown above a simulator on the Simulate tab (matches `ConceptSwitcherTabs`' look: `bg-surface-secondary` backdrop, active pill `bg-surface shadow-md`). Renders `null` for <2 scenarios, so a single-scenario simulator never shows a pointless one-item switcher. Each simulator root renders it only when passed `showScenarioSwitcher` — the homepage Hero omits the prop, so the hero variant has no switcher.
- **`SimulatorRootProps`** (Feature 23, in `types.ts`) — `{ showScenarioSwitcher?: boolean; onReachedEnd?: () => void }`, the shared prop contract every simulator root now accepts. Both default off, so `<XSimulator />` with no props is the unchanged hero behaviour. `onReachedEnd` is a generic "reached the final frame" lifecycle callback (fired once per arrival via a ref-synced effect in each hook) — it keeps the simulator network-free; the host wires it to side effects like the progress POST.

### ConceptSimulator (Feature 23 — Simulate tab host)

File: `src/components/simulators/ConceptSimulator.tsx`

`"use client"`. The Simulate-tab wrapper, mounted via the concept `page.tsx` and passed down as the `simulateContent` prop (same children-as-props pattern as `understandContent`). Lives in `components/` (not `features/learn`) specifically so it can import the simulator **features** directly — the same `components/` → `features/` crossing the homepage `Hero` already uses; a feature importing another feature is forbidden, so the learn feature never touches the simulators.

Props: `{ conceptSlug, conceptId, isLoggedIn, initialCompleted }`. Holds a `SIMULATOR_BY_SLUG` registry (`event-loop` / `react-rendering` / `browser-rendering-pipeline` / `css-specificity` — the seed slugs); an unknown slug renders a "Interactive simulator coming soon" empty state (matches `TabPlaceholder`'s dashed style). Renders the matched simulator with `showScenarioSwitcher` on, and an `onReachedEnd` that POSTs `{ conceptId, tab: "simulate" }` to `/api/progress` — **logged-out is silent** (no POST, no redirect), the POST is guarded fire-once by a ref (seeded `true` when already complete), and a non-OK response resets the guard to allow a retry on the next play-through (429/error handling mirrors `MarkUnderstoodButton`). On success shows a small "Simulator completed" `bg-success-muted` indicator above the simulator.

This shipped a real bug, caught only through direct DOM inspection (not visually obvious in every screenshot): a letter's *pre-trigger* resting transform was `rotateX(-90deg)`, which collapses that letter's rendered bounding box to **zero height** (no `perspective` is set, so the 3D rotation fully foreshortens). A zero-area element can fail to ever register as "intersecting" with Framer Motion's IntersectionObserver-based `whileInView`, so some letters (observed: the first 3 letters of "Simulate" on mobile) got permanently stuck invisible at `opacity: 0`, while sibling letters on the exact same line happened to trigger fine — a non-deterministic, hard-to-spot failure mode. Fixed by moving the single `whileInView`/`viewport` trigger to the **parent container only** (which always has a healthy, non-degenerate bounding box) and propagating the reveal to children via Framer Motion's `variants` + `transition: { staggerChildren }` — the idiomatic Framer Motion pattern for "stagger a group of children," and one that never asks a tiny/transformable element to self-report its own visibility. Also softened the flip angle from `-90deg` to `-60deg` as a second safety margin against any future zero-area edge case. **If anything in this codebase ever needs a per-letter or per-item entrance animation again, observe the parent, not each tiny child — this is the reason why.**

For the swap-pair letters specifically: `dx` (how far a letter must travel) is computed via `useLayoutEffect` measuring each letter span's real `getBoundingClientRect().left` once mounted (re-measured on window resize, debounced via the resize listener itself, since the same word renders at different font sizes per breakpoint) — not a hardcoded pixel value, so it self-adjusts to whatever font size/weight/breakpoint is in play.

### Code-Execution Sandbox (Feature 24, engine promoted in Feature 26)

**The run engine is now shared, not Practice-only:** `src/lib/sandbox/` (`runInSandbox`, `buildSandboxDoc`, `types.ts`) + `src/hooks/useSandbox.ts` — promoted out of `features/practice/sandbox/` in Feature 26 so the Build tab (a separate feature) can use the identical engine without a `features/` → `features/` import (the same precedent as Feature 10 promoting `simulator-chrome` to `components/shared/` + `hooks/` when a second simulator needed it). Runs user JS in a hidden, isolated iframe (`sandbox="allow-scripts"`, **no** `allow-same-origin`), `postMessage` only, per `security.md` → Code Execution Security.

- **`buildSandboxDoc(userCode, tests, nonce, timeoutMs=12000)`** — `lib/sandbox/buildSandboxDoc.ts`. Returns the iframe `srcdoc`: (1) an early `error` recorder (display-only `window.__ffEarlyError` string, no secrets); (2) the user code in its **own** `<script>` (a syntax error there can't stop the harness; its top-level declarations become globals the tests call); (3) an authored-tests runner closure that owns a self-clearing timeout guard and posts one `RESULT`. The per-run `nonce` and the `post`/`finish` plumbing live **only inside the runner closure** (never on `window`), so user submission code can't read the nonce or forge a `RESULT` to bypass the tests. Injects `assert`/`assertEqual`/deep-`eq`/`delay` helpers into test scope. Escapes `</script>` in user code; every message carries `nonce`.
- **`runInSandbox(userCode, tests): Promise<SandboxRunResult>`** — `lib/sandbox/runInSandbox.ts`. Creates the hidden iframe, listens on `message` filtered by `nonce`, 13s parent timeout (> the inner 12s guard), tears down the iframe + listener before resolving. Resolves once, never rejects. **Timeouts widened from 5s/6s during Feature 27** — a correct solution's real iframe run already costs ~2s on its own (fresh JS context + postMessage round-trip); a live user report of a *correct* reference solution timing out traced to that thin margin being eaten by real dev-mode main-thread contention (Turbopack HMR/React/Monaco sharing the thread with the sandboxed iframe), not a logic bug — confirmed by re-running the same solution + tests in plain Node (344ms) and in an isolated bare-browser harness (~2.1s, passing).
- **`useSandbox()`** — `hooks/useSandbox.ts`. `'use client'`. Returns `{ status: "idle"|"running"|"done", result, run(code, tests), reset() }`; `run()` returns the `SandboxRunResult` and ignores re-entrant calls.
- **Types** (`lib/sandbox/types.ts`, re-exported from `lib/sandbox/index.ts`): `SandboxTest { label, source }`, `TestResult { label, passed, error? }`, `SandboxRunResult { results, error }`. `SandboxStatus` is exported from `hooks/useSandbox.ts`.
- **Per-feature test content stays with its feature** — `getTestSpec(slug)` (Practice's challenges, `features/practice/sandbox/testSpecs.ts`) and `getBuildTestSpec(slug)` (Build's project briefs, `features/build/data/testSpecs.ts`) are separate `Record<string, SandboxTest[]>` lookups; only the engine is shared. `features/practice/sandbox/index.ts` re-exports the promoted engine pieces from `lib/sandbox`/`hooks/useSandbox` so existing Practice call sites didn't need an import-path change.
- **Production CSP:** the sandbox requires `frame-src 'self'` (set in `next.config.ts`, Feature 24); the srcdoc's inline harness inherits the page `script-src 'self' 'unsafe-inline'`.

### Spaced Repetition Review Session (Feature 32)

Ran the `architect` skill before building. The core discovery: `user_interview_reviews`'s SM-2 columns (`easeFactor`/`intervalDays`/`repetitions`/`nextReviewAt`) and the Get Started page's Review Queue section (Feature 30) already existed, but nothing had ever computed real scheduling — Learn's Interview-tab rating route (Feature 25) only wrote `quality`/`repetitions`, so the due-queue was permanently empty for every user. This feature is that missing write path, plus the dedicated session UI build-plan.md always specified.

- **`sm2.ts`** — `features/interview-prep/spaced-repetition/sm2.ts`. Pure SM-2 algorithm, no DB/framework dependency (build-plan.md's named location for it) — `applySm2Rating({easeFactor, intervalDays, repetitions}, quality, now?)`. Standard SuperMemo formula, ease factor floored at 1.3, quality < 3 resets `repetitions`/`intervalDays` to 0/1 without discarding the accumulated ease factor. Unit-verified via a disposable standalone script (not committed) against known reference sequences: repeated "Easy" grows intervals 1→6→16→45→131 with ease climbing 2.5→3.0; "Forgot" after 3 reps resets to interval 1/reps 0 while dropping ease correctly; repeated "Hard" floors ease at 1.3 while intervals still grow (1→6→8→10).
- **`applyInterviewReview`** — `lib/progress/applyInterviewReview.ts`. Shared transactional helper (mirrors `applyProgressUpdate`/`applyChallengeSubmission`'s lock-then-write idiom: insert-or-do-nothing to guarantee the row exists, then `SELECT ... FOR UPDATE`, so two concurrent ratings of the same question can't race). Runs `sm2.ts` against the existing row (or SM-2's documented defaults — ease 2.5/interval 1/reps 0 — on a first-ever rating), writes the new scheduling + `quality`/`lastReviewedAt`. Takes an `awardXp` flag: when true, also awards `INTERVIEW_ANSWERED_XP` (10, `lib/constants.ts`) via an `interview_answered` `xp_events` row and bumps the daily streak (once per UTC day) exactly like `applyProgressUpdate`'s streak block. The **only** caller-side difference between the two rating routes below is this one boolean.
- **`/api/interview-rating`** (Learn's Interview tab, Feature 25) — request/response contract unchanged; internals swapped from an inline `onConflictDoUpdate` to `applyInterviewReview(tx, userId, questionId, quality, false)`. `awardXp: false` — this tab already has its own separate 20 XP tab-completion reward (`TAB_XP_REWARDS.interview`), so it deliberately doesn't also earn `interview_answered` XP for the same rating action.
- **`/api/interview-review-rating`** — new route, this feature's own. `{ questionId, quality }` where `quality` must be exactly one of `1|3|4|5` (Forgot/Hard/Okay/Easy — build-plan.md's Feature 32 spec; there's no button for quality `2`, that value is Learn-tab-only). Own rate-limit bucket. Calls the same helper with `awardXp: true`, returns `{ success, xpAwarded }`.
- **`getDueReviewSession(userId)`** / **`getIsPremiumUser(userId)`** — `features/interview-prep/lib/queries.ts`. The former loads the *entire* due set (`nextReviewAt <= now`, no `limit()` — unlike `getReviewQueuePreview`'s 5-item homepage teaser) with the full question shape (`answer`/`companies`/`isPremium`) the session page needs. The latter duplicates `features/learn`'s `getIsPremiumUser` query locally rather than importing it — features never import other features (architecture.md's invariant).
- **Page — `/interview-prep/review`** (`src/app/(app)/interview-prep/review/page.tsx`) — personalization-gated, not premium-gated: a plain `getCachedSession()` check + `redirect("/login?callbackURL=/interview-prep/review")` for logged-out visitors, since this route isn't in `proxy.ts`'s (deliberately short) matcher list. Loads the due queue + premium status in parallel, strips locked answers and computes `isLocked` server-side per question (same pattern as `ConceptInterview`/`QuestionCard` — security.md, premium gating is never client-side only). Empty due queue renders an honest "You're all caught up" state (same precedent as the Review Queue section itself), not a 404.
- **`ReviewSession`** — `features/interview-prep/components/ReviewSession.tsx`. `'use client'`. One question at a time from the fixed queue loaded at page-load (no mid-session re-fetch): difficulty/company chips → question → Show Answer → the answer (`Markdown`, or the premium teaser if locked) → 4 rating buttons (Forgot/Hard/Okay/Easy, POSTs to `/api/interview-review-rating`, advances on success, surfaces a retry note on failure — same `saveFailed` pattern as `QuestionCard`). A `role="progressbar"` bar + "`N` remaining" counter up top. End-of-session summary: total reviewed, a per-rating tally, total XP earned this session, links back to `/interview-prep` and a "Check for more" refresh.

#### Second same-session follow-up: real sizing bug fix, drag re-fix, copy + share buttons

- **`ComparePane`'s box sizing rebuilt around a `ResizeObserver`, not CSS alone — the CSS-only approach was a genuine dead end, not just imperfect.** The screenshot showed the compare box stopping well short of the fullscreen button, and fullscreen mode not visibly changing anything. ### Roadmap Detail Page — Static Flow Diagram (Feature 35)

- **`features/roadmaps/lib/canvasLayout.ts`** — fixed node dimensions (`TOPIC_NODE_WIDTH/HEIGHT` 220×64, `SECTION_NODE_WIDTH/HEIGHT` 200×40) that every authored `position_x`/`position_y` in `scripts/seed/roadmaps.ts` assumes. `buildEdges()`: every node with a `parent_id` connects to it; every root-level node (no parent) chains to the previous root **within the same authored column** (grouped by shared `positionX`) — connecting all roots in one global Y-sorted chain regardless of column was the first version, and produced a stray diagonal line jumping between the Frontend Developer roadmap's two columns whenever their section lengths drifted out of vertical sync.
- **`features/roadmaps/hooks/useCanvasPanZoom.ts`** — pan/zoom over a CSS `transform`, no dependency (same in-house precedent as Feature 49's `rough.js` diagrams). ### Leaderboard Page (Feature 36)

`/leaderboard` — one Server Component page, no client-side data fetching. Built and verified on `feature/36-leaderboard-page`, not yet merged; see `progress-tracker.md`'s Feature 36 entry for the full build/decision narrative.

- **`features/leaderboard/lib/dateRanges.ts`** — `getRangeStart(range)`: `null` for `all-time`, otherwise the current UTC calendar week's Monday (ISO weekday math) or the current UTC calendar month's 1st. Same UTC day-boundary convention the streak system already uses — a fixed reset schedule, not a rolling trailing window.
- **`features/leaderboard/lib/queries.ts`** — **this codebase's first raw-SQL-window-function query.** `getLeaderboardEntries(range)`: All Time ranks directly off `profiles.xp` via `rank() over (order by xp desc)`; Week/Month rank off a live `SUM(xp_events.xp_amount)` grouped by user in the UTC window, same `rank()` window function over the aggregate. Every numeric window/aggregate expression is cast `::int` in the `sql` template — Postgres returns `bigint`/`numeric` for `rank()`/`sum()`, which node-pg hands back as a string unless cast. Capped at the top 100 (`LEADERBOARD_PAGE_SIZE`). Concepts Completed is a second, separate query (`getConceptsCompletedCounts`, `inArray` scoped to just the ids already on the page) rather than a join into the ranking query — joining `user_concept_progress` directly into the Week/Month query's `GROUP BY` would fan out rows before the XP `SUM` aggregates, corrupting it. `getUserRank(userId, range)` is an independent `COUNT(*) + 1` query (a Drizzle subquery via `.as()` for the Week/Month case, since it needs to compare against a per-user aggregate) — this is what makes the "Your Rank" card correct even when the user is outside the top 100, without ever fetching every profile. Both queries use `rank()`, not `row_number()`, specifically so tied scores share a rank number — matching `getUserRank`'s `COUNT+1` formula's own tie semantics (a `row_number()`-ranked table next to a `COUNT`-based single lookup would disagree on ties otherwise). A user with zero `xp_events` in the active Week/Month window simply doesn't appear in that table at all (only `getUserRank` — a separate query — can still place them, e.g. "#2 of 2") — there's no value padding the table with tied-at-zero rows. **CodeRabbit review fix:** added migration `0026_leaderboard_query_indexes.sql` — `profiles_xp_idx` (`profiles.xp`, backs the All Time `ORDER BY`/`WHERE xp >` queries) and `xp_events_user_id_created_at_idx` (composite `(user_id, created_at)`, backs `getUserRank`'s Week/Month per-user range-sum lookup) — neither existed before, since this feature is the first thing in the codebase to actually query `xp_events` rather than just insert into it. **A follow-up CodeRabbit round suggested `CREATE INDEX CONCURRENTLY` for both, to avoid a regular `CREATE INDEX`'s write-blocking lock on deployment — skipped, verified against this codebase's actual migration runner rather than applied blindly:** `drizzle-orm/pg-core/dialect.js`'s `migrate()` wraps every pending migration in one `session.transaction(...)` call, and Postgres hard-errors if `CREATE INDEX CONCURRENTLY` runs inside a transaction block — so this suggestion, applied as written, would have broken `npx drizzle-kit migrate` outright the next time it ran (for this migration and every other pending one in the same batch), not just been suboptimal. Doing it properly would mean building a net-new non-transactional migration/deployment path with no precedent across this project's other 26 migrations — disproportionate for a pre-launch app with a two-row `profiles` table and no live production traffic yet. Left as a deferred item for whenever real production traffic and a proper zero-downtime migration process are actually needed (see `progress-tracker.md`'s Feature 36 entry).
