"How would you manage state for this?" is one of the most reliably-asked follow-ups in a frontend system design round, and the weakest answers jump straight to naming a library (Redux, Zustand, React Query) without addressing the actual design question underneath: what kinds of state exist here, and how do they interact?

## The first split: server-cache state vs. client-only state

Almost every real system design prompt involves at least two categorically different kinds of state, and conflating them is the most common mistake:

| | Server-cache state | Client-only UI state |
|---|---|---|
| Example | Feed items, a document's content, search results | Modal open/closed, active tab, scroll position, unsubmitted form input |
| Can go stale? | Yes — needs invalidation | No server counterpart to go stale against |
| Where it should live | A dedicated data-fetching/caching layer, not hand-rolled `useState`/`useEffect` | As close as possible to the component that owns it |

Naming this split explicitly, before touching implementation, is itself a strong signal — it shows you're not going to reach for one tool to solve two structurally different problems.

## Optimistic updates, and how they fail gracefully

A "like" button, a new comment, a reordered list — many frontend system design prompts expect optimistic UI (update immediately, reconcile with the server response after) rather than waiting on a round trip. The part candidates often skip is the failure path: what happens when the optimistic update's server request fails? A complete answer names the rollback — reverting the local state to its prior snapshot and surfacing an error — not just the happy-path optimistic update itself.

## Synchronizing multiple data sources

Real-time features add a second complication: state can now change from more than one source — a user's own optimistic action, and an incoming real-time event from another user or device. A collaborative canvas or document editor has to reconcile these without one silently overwriting the other. Naming the specific strategy (last-write-wins with a timestamp, an operational-transform or CRDT-based merge, or a simpler "reject the local change if the server disagrees" approach) — and the tradeoff each implies — is exactly the kind of reasoning [FF Frontend System Design's collaborative guides](/interview-prep/ff-system-design/collaborative-canvas-design-tool) walk through in full.

## When a dedicated store earns its complexity

The same tradeoff from [Whiteboarding React Architecture Without Code](/interview-prep/playbook/react-interview-playbook/whiteboarding-react-architecture-without-code) applies at system-design scale, just with higher stakes: a dedicated store or a data-fetching library (React Query, SWR, or similar) earns its cost when state needs to be shared broadly, cached across navigations, or synchronized against a real-time source — not by default for every feature, and naming that boundary explicitly is stronger than reflexively reaching for the heaviest tool available.

## A concrete way to structure the answer

When a prompt asks about state management, a strong structure is: name the categories of state present (server-cache vs. client-only vs. real-time-synced), name where each lives and why, name the optimistic-update and rollback strategy if relevant, and only then name the specific tool or pattern you'd reach for. Answers that start and end with a library name, with no reasoning in between, read as surface-level regardless of whether the library choice itself was reasonable.
