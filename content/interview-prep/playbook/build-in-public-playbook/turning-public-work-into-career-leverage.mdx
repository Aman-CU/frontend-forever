Doing the work described in this playbook — sharing progress, contributing to open source — only pays off if it's actually visible at the moments that matter: the resume scan, the portfolio click-through, the interview answer. This chapter is about connecting the two halves.

## Put it where the 8-second scan can find it

A recruiter skimming a resume for a few seconds (see [What Recruiters Scan For in 8 Seconds](/interview-prep/playbook/frontend-resume-playbook/what-recruiters-scan-for-in-eight-seconds)) will never find a contribution buried three pages deep on your blog. A real, merged open source contribution belongs as its own resume line when it's substantial enough — "Contributor to [project] (12k+ GitHub stars) — merged 3 PRs improving cache invalidation and test coverage" is a stronger signal than most side projects, precisely because it's independently verifiable by anyone who clicks through. See [Which Projects to Feature](/interview-prep/playbook/frontend-resume-playbook/which-projects-to-feature) for how it should sit alongside your other project material, not replace it.

## Pin it, don't bury it

On GitHub specifically, a pinned fork or a pinned repo showing your own tooling built around an open source project you contribute to puts the work exactly where a recruiter's click-through lands first — see [Cleaning Up Your GitHub and Portfolio](/interview-prep/playbook/frontend-resume-playbook/cleaning-up-your-github-and-portfolio) for the mechanics of pinning and README quality. A genuinely good contribution that's one of forty unpinned repositories on your profile might as well not exist to someone skimming for ten seconds.

## Build the interview story before you need it

The same discipline covered in [Building Your Personal Story Bank](/interview-prep/playbook/behavioural-interview-playbook/building-your-personal-story-bank) applies directly here — a real open source contribution is exceptionally strong raw material for a technical or behavioral story, because unlike most work examples, an interviewer can actually go read the pull request, the review discussion, and the final merged diff themselves. Prepare the story in advance: what the bug or feature was, why your specific approach was the right one, what pushback you got in review and how you responded to it. That last part — responding to real, external code review from a maintainer with no obligation to be gentle — is a genuinely good behavioral-interview answer to "tell me about a time you received difficult feedback."

## Let it answer the "why should we trust your code quality" question before it's asked

A portfolio project is code nobody else has ever had a reason to push back on. A merged open source PR is code that passed a stranger's scrutiny, with no professional obligation to be kind about it. Naming this distinction directly in an interview — "this PR went through two rounds of review from a maintainer I'd never worked with before, and here's what changed as a result" — answers a skepticism a portfolio project can't fully address on its own.

## Don't force a fit that isn't there

Not every open source contribution or every public post belongs on a resume — a single small documentation fix from years ago isn't resume material the way a sustained pattern of contributions to one project is. Apply the same bar from [Which Projects to Feature](/interview-prep/playbook/frontend-resume-playbook/which-projects-to-feature): does this genuinely demonstrate something your other material doesn't already show? If not, it can stay a quiet part of your GitHub history without needing to be surfaced everywhere.

## The compounding payoff

None of this needs to happen all at once, and it doesn't need a large following behind it — a single well-documented, well-placed contribution, properly surfaced on a resume and ready as an interview story, outperforms a large scattered public presence with nothing concrete to point to. See [Avoiding Burnout and Staying Consistent](/interview-prep/playbook/build-in-public-playbook/avoiding-burnout-and-staying-consistent) for how to keep building this over time without it becoming exhausting.
