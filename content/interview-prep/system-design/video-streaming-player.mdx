## 1. Requirements Gathering

**Functional requirements:**

- Play a video with standard controls (play/pause, seek, volume, fullscreen, playback speed).
- Automatically adjust quality to the viewer's actual network conditions, with a manual override option.
- Support captions/subtitles and multiple audio tracks.
- Resume playback from where the viewer left off on a previous session.

**Non-functional requirements:**

- Playback must start quickly and must not stall (buffer/rebuffer) under normal network conditions — rebuffering is the single most damaging playback experience for viewer retention.
- Must adapt gracefully to changing network conditions mid-playback, both degrading and recovering quality without a jarring, disruptive switch.
- Must work across a wide range of devices/browsers with differing native video/codec support.

**Explicitly out of scope:** the video encoding/transcoding pipeline and CDN infrastructure — this guide covers the client player's segment-fetching, bitrate-adaptation, and buffering architecture, treating the encoded segment tiers as already available from the server. The [Audio Streaming Player guide](/interview-prep/ff-system-design/audio-streaming-player) covers the same adaptive-delivery ideas applied to a lighter-weight, audio-only case.

## 2. Constraints & Estimation

- **Adaptive bitrate (ABR) streaming is universal across real video platforms** — every major streaming product encodes the same video into several quality/bitrate tiers, splits each tier into short segments (commonly a few seconds each), and lets the client choose which tier to request per segment based on current conditions, rather than committing to one fixed quality for the whole playback.
- **Bandwidth estimation is commonly throughput-based**: the player estimates available bandwidth largely from how long the most recently downloaded segment took relative to its size, then selects the highest quality tier whose bitrate comfortably fits that estimate — a reactive approach (it responds to bandwidth that has already changed, not bandwidth about to change), which is a genuine, acknowledged limitation of the simplest ABR algorithms.
- **Buffer health matters as much as raw bandwidth** — a player with a healthy multi-segment buffer can afford to ride out a brief bandwidth dip without switching quality at all; a player with a thin buffer needs to react more conservatively, since it has less runway before a stall.
- **Standard protocols (HLS, MPEG-DASH) define the segment/tier manifest format** the player consumes — the actual video decoding and buffering in the browser is generally done via the Media Source Extensions (MSE) API, since neither protocol is natively understood by the `<video>` element without a JavaScript layer feeding it segments through MSE. The one real exception: Safari (desktop and iOS) has native HLS support built into `<video>` itself — an `.m3u8` manifest can be set directly as the `src` and Safari handles segment fetching and ABR internally, no MSE or JavaScript player logic required. DASH has no equivalent native support anywhere, and browsers other than Safari have no native HLS support either, which is why a real player still needs the full MSE-driven path as the general case, using native HLS only as a Safari-specific shortcut.
- **A worked tier-selection estimate**: at a 4-second segment duration, a 1080p tier (~6Mbps) needs the client to sustain ~3MB/segment-interval; on a connection that's just measured ~4Mbps of throughput, the 480p tier (~2.5Mbps, ~1.25MB/segment-interval) is the highest one that fits with real margin — this is literally the arithmetic the ABR Controller runs on every segment decision, just automated rather than manual.

## 3. Data Contract Design

```
// Manifest (simplified DASH/HLS-style shape)
{
  "renditions": [
    { "bitrate": 800000, "resolution": "426x240", "segmentTemplate": ".../240p/seg-$Number$.m4s" },
    { "bitrate": 2500000, "resolution": "854x480", "segmentTemplate": ".../480p/seg-$Number$.m4s" },
    { "bitrate": 6000000, "resolution": "1920x1080", "segmentTemplate": ".../1080p/seg-$Number$.m4s" }
  ],
  "segmentDurationSec": 4
}

// Player-internal state per segment fetch
{ "segmentIndex": 42, "renditionBitrate": 2500000, "downloadMs": 850, "byteSize": 265000 }
```

- **The manifest describes tiers and how to construct segment URLs**, not the video bytes themselves — the client fetches this once at playback start (and periodically re-fetches for a live stream), then independently requests individual segments as playback progresses.
- **Each segment fetch's timing is retained** (at least the most recent few) specifically to feed the bandwidth-estimation logic — `downloadMs` versus `byteSize` is the raw signal the ABR algorithm's throughput estimate is built from.
- **Segments are fetched independently per rendition tier** — switching quality means simply requesting the next segment index from a different rendition's `segmentTemplate`, not re-fetching or transforming anything already buffered.

## 4. High-Level Component Architecture

<ArchitectureDiagram />

- **Manifest Parser** — fetches and parses the tier/segment manifest, exposing the available renditions and segment addressing scheme to the rest of the player.
- **Bandwidth Estimator** — tracks recent segment download timing/size to maintain a rolling estimate of available throughput.
- **ABR Controller** — given the Bandwidth Estimator's current estimate and the buffer's current health, decides which rendition tier the *next* segment fetch should target.
- **Segment Fetcher/Buffer** — downloads segments for the ABR Controller's chosen tier and feeds them into the browser's Media Source Extensions buffer, which the native `<video>` element then plays from.
- **Playback Controller** — the user-facing controls (play/pause/seek/volume), translating user actions into either native `<video>` element calls or, for seeking, a request to fetch and buffer segments starting from the new position.

## 5. State Management Design

- **Bandwidth estimate and buffer health are the two inputs the ABR Controller's decision depends on** — modeled as continuously-updated state, not recomputed from scratch on each decision, since both should reflect a rolling window of recent history rather than only the single most recent data point.
- **The currently-selected rendition tier is explicit state**, distinct from "the tier of whatever's already buffered" — since a quality switch only affects segments fetched *from now on*, already-buffered segments at the old tier still play out before the new tier's segments are reached.
- **Playback position (current time) is read from the native `<video>` element itself** as the source of truth for "where is the viewer in the video," with the buffering/fetching logic working ahead of that position rather than needing to independently track it.

## 6. Deep Dives

### The throughput-based ABR decision loop

Before requesting each new segment, the ABR Controller: (1) checks the Bandwidth Estimator's current throughput estimate, (2) checks how much buffer is currently held (more buffer = more tolerance for a lower-confidence quality choice), and (3) selects the highest rendition tier whose bitrate comfortably fits within the estimate, generally with some safety margin rather than the theoretical maximum the estimate would allow. This is explicitly reactive — it can only respond to bandwidth conditions the *previous* segment's download already revealed, which is why real implementations bias conservatively rather than aggressively chasing the highest tier the last measurement alone would justify.

```ts
function selectRendition(renditions: { bitrate: number }[], estimatedBps: number, safetyMargin = 0.8) {
  const affordable = renditions.filter((r) => r.bitrate <= estimatedBps * safetyMargin);
  if (affordable.length) return affordable.reduce((best, r) => (r.bitrate > best.bitrate ? r : best));
  // Manifests aren't guaranteed to list renditions in bitrate order, so the
  // fallback has to compute the actual lowest tier rather than assume it's
  // renditions[0] — picking the wrong one here defeats the whole point of a
  // conservative fallback.
  return renditions.reduce((lowest, r) => (r.bitrate < lowest.bitrate ? r : lowest));
}
```

### Segment-boundary switching, not mid-segment

Quality switches happen between segment fetches, never mid-segment — a single segment is always played at the single quality it was encoded and downloaded at, since decoding a segment at a mixed quality isn't a coherent operation. This is why segment duration is itself a real design parameter: shorter segments allow finer-grained, faster-reacting quality adjustments (more switch opportunities per unit of playback time) at the cost of slightly more request overhead; longer segments reduce request overhead but make the player slower to react to a sudden bandwidth change.

### Buffering strategy and startup latency

Starting playback requires buffering at least one segment before the `<video>` element can begin — real players commonly start with a conservative (lower) quality tier for the very first segment specifically to minimize startup latency, then let the ABR Controller ramp quality up once the Bandwidth Estimator has real data and the buffer has built a healthy cushion, rather than guessing at a high quality tier for the critical first segment.

### Media Source Extensions as the buffering mechanism

Since HLS/DASH generally aren't natively understood by the `<video>` element, the player uses MSE to feed downloaded segment bytes into a `SourceBuffer` that the native element decodes and plays from — this is the mechanism that makes JavaScript-driven, protocol-aware adaptive streaming possible at all inside a standard browser video element, rather than needing a plugin or a fully custom decoder. A real player still checks for Safari's native HLS support first (via `video.canPlayType`) and skips its own MSE path entirely there, falling back to MSE everywhere else and for DASH unconditionally.

## 7. Performance & UX Tradeoffs

| Decision | Favors | Costs |
| --- | --- | --- |
| Aggressive quality selection | Best visual quality the last estimate allows | Real stall risk the moment conditions worsen slightly |
| Conservative quality selection (with margin) | Meaningfully lower stall risk | Slightly lower visual quality than the estimate would allow |
| Short segments (e.g. 2-4s) | ABR reacts fast to changing conditions | More HTTP request overhead |
| Long segments (e.g. 6-10s) | More efficient per byte | Slower to adapt to a sudden bandwidth change |
| Deeper pre-fetch buffer | Tolerates longer bandwidth dips without stalling | More memory held, possibly wasted if the viewer seeks/stops |

Most real streaming products bias toward the conservative-quality, shorter-segment combination — a visible stall costs far more perceived quality than a slightly-lower-than-optimal bitrate ever does.

## 8. Follow-ups

- **"What if the viewer seeks to an unbuffered part of the video?"** The player needs to abandon (or deprioritize) in-flight fetches for the old position, and immediately begin fetching from the new position — typically restarting from a conservative quality tier at the new position, the same reasoning as the initial-playback startup case, since there's no recent bandwidth/buffer history relevant to the new position.
- **"How would live streaming change this design?"** A live manifest continuously appends new segments rather than describing a fixed, complete set — the player needs to periodically re-poll the manifest for newly available segments and manage how close to the "live edge" it plays from, a meaningfully different buffering posture than on-demand video's "the whole timeline already exists" assumption.
- **"How do you test ABR logic without relying on real, variable network conditions?"** Mock the Bandwidth Estimator's inputs with fixed, scripted download-timing sequences (simulating a bandwidth drop then recovery) and assert the ABR Controller selects the expected rendition tier at each step — deterministic and fully testable without an actual flaky network.
- **"What if a specific rendition tier's segment fails to load?"** The player should fall back to a lower-tier request for that same segment index rather than stalling entirely — a graceful-degradation path distinct from the normal proactive ABR decision.
