## 1. Requirements Gathering

**Functional requirements:**

- Boards/lists of tasks (issues, cards) that can be created, edited, reordered, and moved between statuses/columns.
- Changes made by any collaborator appear live for everyone viewing the same board.
- The app remains fully usable offline — creating and editing tasks — with changes syncing once connectivity returns.
- Reordering tasks within and across columns (drag-and-drop) with the new order visible instantly and consistently for all viewers.

**Non-functional requirements:**

- Every local action (creating a task, dragging a card) must feel instant, never waiting on a network round-trip before updating the UI.
- The app must function with the network layer entirely absent — not degraded, genuinely functional — since this is a stated design goal of real products in this category, not just a nice-to-have offline fallback.
- Reordering must have a conflict resolution strategy that doesn't require heavy per-edit coordination, since drag-and-drop reordering is a very frequent, low-stakes operation compared to something like simultaneous rich-text editing.

**Explicitly out of scope:** the specific UI drag-and-drop library/mechanics and the backend's storage schema — this guide covers the client-side sync engine architecture that makes real-time, offline-capable collaboration possible.

## 2. Constraints & Estimation

- **A local-first architecture inverts the usual client-server relationship**: the client's local, in-memory object graph is authoritative for the UI immediately, and network sync happens asynchronously in the background — real products in this category are built this way explicitly so the app "doesn't even need the network to function," not merely so it degrades gracefully when offline.
- **A persisted transaction/mutation queue is the mechanism that survives being offline** — every local mutation is both applied to the in-memory graph immediately *and* appended to a durable local queue (commonly IndexedDB); reconnecting simply means draining that queue against the server, with no special-cased "recovering from offline" code path distinct from normal operation.
- **Conflict resolution for this category tends toward simple, not exotic** — full CRDTs are used sparingly even in real, sophisticated local-first products (commonly reserved for genuinely rich content like a description field's text), while most fields (status, assignee, position) use straightforward last-writer-wins, since true simultaneous conflicting edits to the same field are rare relative to the volume of non-conflicting concurrent activity across a whole team's board.
- **Reordering needs a representation that avoids mass-renumbering on every drag** — the same fractional-indexing technique used for design-tool layer ordering applies directly here: a task's position is a sortable value that can always have a new value generated between two neighbors, so moving one card never requires rewriting every other card's position.
- **A concrete mutation-volume estimate**: an active team board sees roughly 500-2,000 task mutations/day across all collaborators (creates, status changes, reorders); at ~150 bytes/mutation, that's under 300KB/day queued in the worst case of everyone being simultaneously offline — small enough that the Mutation Queue's storage cost is never the constraint, sync-request batching (section 3) is about request count, not payload size.

## 3. Data Contract Design

```
// A task/issue object in the local graph
{
  "id": "task_771",
  "title": "...",
  "status": "in_progress",
  "assigneeId": "u_4",
  "position": "a3|f", // fractional index within its column
  "updatedAt": "2026-07-18T10:00:00Z"
}

// A queued local mutation, persisted to IndexedDB until synced
{
  "mutationId": "m_1029",
  "type": "update_task",
  "taskId": "task_771",
  "changes": { "status": "done" },
  "createdAt": "2026-07-18T10:05:00Z",
  "synced": false
}

// A remote change event (over WebSocket, once online)
{ "type": "task_changed", "taskId": "task_771", "changes": { "status": "done" }, "revision": 552 }
```

- **Every local mutation is durably queued before (or as) it's applied**, not applied optimistically-in-memory-only and separately "remembered" some other way — the queue *is* the mechanism that survives a page reload or extended offline period without losing pending work.
- **`position` uses the same fractional-indexing pattern** as the [Collaborative Canvas Design Tool guide](/interview-prep/ff-system-design/collaborative-canvas-design-tool)'s layer ordering — reordering a task is a single-field update to that one task's position, never a bulk update of every other task's position in the column.
- **Remote change events carry only the changed fields**, applied as a patch onto the existing local object, consistent with how the client's own local mutations are also represented as patches, not full-object replacements.

## 4. High-Level Component Architecture

<ArchitectureDiagram />

- **Object Graph** — the normalized, in-memory representation of all tasks/boards the client currently has loaded, treated as authoritative for every read the UI performs.
- **Mutation Queue** — every local write (create, update, reorder) is appended here and persisted to IndexedDB immediately, independent of current connectivity.
- **Sync Engine** — drains the Mutation Queue against the server when online, and applies incoming remote change events onto the Object Graph — both directions funnel through the same conflict-resolution logic (predominantly last-writer-wins per field).
- **Reactive View Layer** — the UI subscribes to the Object Graph and re-renders when relevant objects change, regardless of whether that change originated locally (optimistic) or remotely (a synced update from a collaborator).

## 5. State Management Design

- **The Object Graph is the single source of truth the UI reads from — always, regardless of connectivity** — there's no separate "offline mode" data path; the UI never talks to the network directly, only to the Object Graph, which the Sync Engine keeps eventually consistent with the server in the background.
- **The Mutation Queue is append-only until synced**, and its persistence (not just in-memory tracking) is what makes "close the tab while offline, reopen later" safe — pending changes survive a full page reload because they were durably queued, not held only in a JS variable.
- **Reconnection has no special-cased state** — the Sync Engine draining a queue with 50 pending mutations after an hour offline runs through the identical code path as draining a queue with 1 pending mutation after a 200ms network blip; the only difference is queue length.

## 6. Deep Dives

### The mutation queue as the offline mechanism

Every user action — editing a task, changing its status, dragging it to a new position — becomes a mutation object appended to a durable queue *before* (or atomically with) updating the in-memory Object Graph the UI renders from. This is what decouples "the UI feels instant and works offline" from "eventually, this needs to reach the server": the UI never waits on the queue draining, and the queue draining never blocks the UI, it just eventually reconciles.

### Conflict resolution: mostly last-writer-wins, CRDTs where it actually matters

Most fields on a task (status, assignee, position) see relatively low real-world contention — two people rarely change the exact same task's status at the exact literal same instant — so a straightforward last-writer-wins-per-field policy is sufficient and far simpler than full conflict-free merge logic. The ordering key matters here: "last" needs to mean the mutation's own client-recorded timestamp (captured the instant the user made the edit, carried with the mutation into the queue), not the order the server happens to receive it in — a receipt-order-based scheme would make the outcome depend on which device's queue happens to drain to the server first, which is exactly the property offline conflict resolution needs to *not* have. Real local-first products in this category have reported adopting CRDTs selectively, specifically for genuinely rich, high-contention content like a long-form description field, rather than applying heavyweight merge logic uniformly across every field — a deliberate, scoped decision rather than a default.

### Fractional indexing for drag-and-drop reordering

Moving a task from one position to another (within a column or across columns) only requires computing a new fractional-index value that sorts correctly between its new neighbors — no other task's stored position needs to change. This is what keeps reordering a cheap, independent, non-conflicting operation even when many users are simultaneously reordering different tasks on the same board.

### Reactive updates regardless of change origin

Because the UI subscribes to the Object Graph rather than directly to "network events" or "local actions" as separate concepts, a task changing status via the local user's own click and a task changing status via a teammate's remote edit both flow through the identical render-update path — the view layer doesn't need separate code for "my own optimistic update" versus "someone else's synced update," which meaningfully simplifies the UI layer.

## 7. Performance & UX Tradeoffs

| Decision | Favors | Costs |
| --- | --- | --- |
| Local-first (client authoritative) | Instant perceived performance, genuine offline capability | Needs a real conflict-resolution/reconciliation strategy |
| Server-authoritative (wait for confirmation) | Server response is simply "the truth" | Every action waits on a round-trip |
| Last-writer-wins per field | Simple, sufficient for status/assignee/position | Rare risk of silently discarding a genuine conflict |
| Full CRDT merging per field | Never silently discards a conflict | Real complexity, only justified for rich fields like descriptions |
| Fractional indexing for position | No renumbering on reorder | Rare rebalancing if many inserts target the same narrow gap |

The last-writer-wins vs. CRDT row is the same field-by-field judgment call as the general [Offline-First Sync Engine guide](/interview-prep/ff-system-design/offline-first-sync-engine) — most fields here land on LWW; only description-style rich text would justify CRDTs.

## 8. Follow-ups

- **"What happens if the same task is edited offline on two different devices, then both come back online?"** Both devices' queued mutations eventually reach the server and get resolved via the same last-writer-wins-per-field policy, compared by each mutation's own client-recorded timestamp (not by which device happened to reconnect/drain first) — the same mechanism handles "two devices" exactly like "two different users," since from the server's perspective both are just two independent mutation streams.
- **"How would you show sync status to the user (e.g. 'syncing...' vs 'all changes saved')?"** Derive it directly from the Mutation Queue's current length/oldest-pending-timestamp — a non-empty queue means "syncing," an empty one means "up to date," without needing separate state tracking duplicating what the queue already represents.
- **"How do you avoid the Mutation Queue growing unbounded if the app is offline for a very long time?"** Real systems generally coalesce redundant mutations to the same field before they're ever sent (e.g. 5 queued status changes to the same task collapse to just the final one) rather than replaying every intermediate edit — reduces both queue size and sync traffic.
- **"How do you test the sync engine's conflict resolution?"** Deterministically simulate two "devices" each queuing conflicting mutations to the same field with known timestamps, drain both queues against a mocked server in varying order, and assert the final state matches the expected last-writer-wins outcome regardless of drain order — correctness here means the *same* final state regardless of reconciliation order, the same convergence property collaborative editors are tested against.
