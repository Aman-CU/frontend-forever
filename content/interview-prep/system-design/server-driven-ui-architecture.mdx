## 1. Requirements Gathering

**Functional requirements:**

- Render a screen's layout and content from a structured description the server returns, rather than from a layout hardcoded in the client.
- Support a defined set of reusable component "types" the server can reference by name, each mapped to a real client-side component.
- Allow the server to change which components appear, in what order, and with what data/props, without a new client release.
- Support targeting different UI variants to different user segments (A/B experiments, gradual rollouts) from the server side alone.

**Non-functional requirements:**

- The client must never crash or render a blank screen when the server references a component type the client doesn't (yet) recognize, *or* when a recognized type's `props` payload is malformed (missing fields, wrong shape) — forward/backward compatibility across client and server versions releasing independently is a core requirement, not an edge case, and a known type with bad data is at least as likely in practice as an unknown type.
- Rendering must stay performant even though the screen's structure is now data-driven rather than statically compiled — parsing and rendering an arbitrary server-described tree shouldn't be meaningfully slower than a hardcoded equivalent.
- The set of server-referenceable component types needs governance — an uncontrolled, ever-growing vocabulary of component types undermines the whole point of a constrained, client-understood rendering contract.

**Explicitly out of scope:** the server-side template/orchestration layer that assembles the UI description (a separate backend architecture concern) — this guide covers the client's interpretation/rendering of whatever structured description it receives.

## 2. Constraints & Estimation

- **The core mental model: the client becomes a rendering engine, not a decision-maker** — real production descriptions of this pattern describe the app as receiving instructions and executing them, capable of displaying whatever the server describes, but no longer independently deciding what gets displayed — a genuine shift in where UI-composition logic lives.
- **This is explicitly valuable where release cycles are the bottleneck** — real case studies (a major travel platform's search/listing/checkout screens, a commerce platform's app-store-screen experiments) describe this specifically solving the problem of app-store review delays blocking fast iteration; a fix or experiment that previously took a release cycle to reach users can ship immediately once the server, not the client binary, controls the relevant screen's structure.
- **A defined, bounded component vocabulary is what keeps this maintainable** — the server can only reference component *types* the client has actually implemented; an unbounded, ad hoc vocabulary (the server inventing new component-type strings the client has no renderer for) is precisely the failure mode the client's fallback-handling requirement exists to survive gracefully, not to enable arbitrarily.
- **A real architectural pipeline typically has three layers server-side**: a template layer defining possible layouts, a data layer fetching the actual content, and an API layer (commonly GraphQL) assembling and delivering the final structured description — the client-facing contract is only this final assembled description, not any of the server-internal layers producing it.
- **A concrete payload-size ceiling is worth naming**: a typical screen description (10-20 sections, each with modest props) serializes to roughly 5-15KB of JSON — trivial against typical page-load budgets, but a screen with hundreds of sections (a long feed described entirely server-side, rather than paginated) would push into the range where the description itself becomes a measurable load-time cost, which is the concrete threshold where this pattern should hand off to the [Infinite-Scroll Feed guide](/interview-prep/ff-system-design/infinite-scroll-feed)'s pagination instead of describing everything in one response.

## 3. Data Contract Design

```
{
  "screen": {
    "sections": [
      { "type": "hero_banner", "props": { "title": "...", "imageUrl": "..." } },
      { "type": "product_carousel", "props": { "items": [ ... ] } },
      { "type": "unknown_future_component", "props": { ... } }
    ]
  }
}
```

- **Every section carries a `type` the client maps to a real, registered component renderer** — the client's rendering logic is a lookup (`type` → component), not a hardcoded sequence of specific components.
- **An unrecognized `type` (from a newer server version than the client's registered set knows about) must be a defined, graceful case** — rendered as nothing (silently skipped) or a minimal, non-breaking placeholder, never a crash or a blank screen, since server and client release independently and the server may reference component types a not-yet-updated client hasn't shipped support for.
- **A recognized `type` doesn't mean trustworthy `props`** — every registered component needs its own runtime schema its `props` are checked against before the component ever renders (expected fields present, roughly the right shape), since the server-described payload is external input the same way an API response is, not something the client's own code produced.

## 4. High-Level Component Architecture

<ArchitectureDiagram />

- **Screen Fetcher** — requests the structured screen description from the server for the current route/context.
- **Component Registry** — a client-side map from `type` string to the actual registered React (or equivalent) component responsible for rendering that section type.
- **Renderer** — walks the fetched description's sections, looks each one up in the Component Registry, and renders the matched component with the given `props`; for an unrecognized `type`, falls back to a defined graceful no-op rather than throwing. Wraps each individual section in its own error boundary, so a component that throws mid-render (most commonly because its `props` failed schema validation, or slipped past it) takes down only that one section, not the whole page.
- **Component Types** — the actual, bounded set of implemented section renderers (hero banners, carousels, forms, etc.), each a normal client component that happens to be invoked indirectly via the Registry rather than referenced directly in a hardcoded screen layout.

## 5. State Management Design

- **The fetched screen description is the primary state the Renderer operates over** — treated as data, re-fetched per screen/route rather than assembled from separate, independently-fetched pieces the client would otherwise need to compose itself.
- **The Component Registry is effectively static configuration**, established at client build/boot time from whatever component types that client version actually implements — it's not something that changes at runtime based on the fetched description.
- **Unrecognized-type handling needs to be genuinely stateless/local to the Renderer's walk** — encountering one unknown type shouldn't affect rendering of the other, recognized sections in the same screen description; each section renders (or gracefully doesn't) independently. The same isolation applies to a recognized type with invalid props: a plain JS try/catch around JSX doesn't catch a render-time throw, so this is specifically what the per-section error boundary is for, not something the Renderer's own control flow can provide on its own.

## 6. Deep Dives

### The client as a rendering engine, not a decision-maker

This is the central conceptual shift server-driven UI represents: in a conventional client architecture, the client's own code decides what screen structure to show (conditionally, based on client-side logic); here, that decision-making moves server-side, and the client's job narrows to faithfully rendering whatever structured description it's handed — which is exactly what makes server-side experimentation and instant fixes possible, since changing *what's shown* becomes a server-side data change, not a client code change requiring a new release.

### Forward/backward compatibility as a first-class design requirement

Because the server and client inevitably release on different cadences (the server can deploy instantly; the client is bound by app-store/browser-cache realities), the server will, at some point, describe a component type a given user's currently-installed client doesn't yet recognize. The Renderer's fallback behavior for an unrecognized type — skip it gracefully, or render a defined minimal placeholder — is not an edge case to patch in later; it's a core requirement the whole architecture depends on to avoid every client version needing to be perfectly synchronized with every server deployment.

### Real production motivations: bypassing release cycles

Documented real case studies describe two distinct motivations converging on the same architecture: a travel platform's engineering team building a system letting servers orchestrate what users see across web and mobile simultaneously without app-store review delays for their highest-traffic screens (search, listings, checkout); and a commerce platform's team specifically citing the ability to launch experiments whenever needed rather than being bound by a fixed weekly release cadence, with fixes that previously took a week to reach users now shippable immediately. Both are the same underlying tradeoff: moving structural UI decisions server-side to escape client-release-cycle latency.

### Governing the component vocabulary

Since the whole architecture depends on the client having a real, implemented renderer for whatever `type` the server references, the set of valid component types can't grow unboundedly or informally — a real system needs some process (a registry review, a defined process for proposing and shipping a new component type) for expanding what the server is allowed to reference, otherwise the server-side team's flexibility outpaces what the client can actually safely render, reintroducing exactly the coordination bottleneck this architecture is meant to remove, just moved to a different layer.

## 7. Performance & UX Tradeoffs

| Decision | Favors | Costs |
| --- | --- | --- |
| Server-driven structure | Instant reshaping, no release cycle | Client can't statically reason about screen shape at build time |
| Hardcoded client layout | Compile-time type-checking of screen structure | Every change needs a client release |
| Bounded, governed component vocabulary | Client rendering surface stays safe/comprehensible | Server team can't ship arbitrary new UI without client registry work first |
| Silent skip for unrecognized types | Simple, never crashes | User on an old client may silently miss content a new server assumes is universal |
| Minimal fallback placeholder for unrecognized types | User sees *something* changed, not silence | More implementation work than a pure no-op |

The last two rows are the real judgment call most implementations get wrong by default (reaching for silent-skip without considering the placeholder alternative) rather than choosing deliberately.

## 8. Follow-ups

- **"How would you test a client that renders an unbounded variety of server-described screens?"** Testing shifts from "does this specific hardcoded screen render correctly" to "does the Renderer correctly map every registered component type, and does it correctly and gracefully handle an unrecognized type" — the Component Registry's mapping and fallback logic become the primary unit-testable surface, largely independent of any one specific screen's actual content.
- **"How would you handle a component type that needs client-side interactive state (e.g. a form)?"** The server describes *that* a form section exists and its initial props/schema, but the actual interactive state (field values, validation) lives and is managed entirely client-side within that registered component — server-driven UI describes structure and initial data, not runtime interaction logic.
- **"What if two different servers/environments describe conflicting versions of the same screen?"** This is generally a backend-orchestration concern (which server/environment is authoritative for a given request) rather than something the client's Renderer needs to resolve — the client's contract is simply "render whatever single, coherent description I was given for this request."
- **"How would you avoid the server-side team building a new component type for every one-off design need?"** The same variant-vs-composition discipline as the [Design System guide](/interview-prep/ff-system-design/scalable-design-system) — a genuinely new, reusable pattern justifies a new registered component type; a one-off tweak is better expressed via props/data variation on an already-registered component type, not a proliferating vocabulary of near-duplicate types.
