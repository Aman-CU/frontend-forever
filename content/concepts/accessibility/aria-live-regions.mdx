## polite vs. assertive

```html
<!-- Waits its turn — won't interrupt whatever is currently being read -->
<div aria-live="polite">3 new results found</div>

<!-- Interrupts immediately — reserve for truly urgent content -->
<div aria-live="assertive">Your session expires in 1 minute</div>
```

Overusing `assertive` is a real cost: every interruption cuts off whatever the screen reader user was already listening to, so most updates — a saved confirmation, a result count — belong in `polite`.

## Shorthand roles

```html
<!-- Equivalent to aria-live="polite" -->
<div role="status">Changes saved</div>

<!-- Equivalent to aria-live="assertive" -->
<div role="alert">Payment failed — please try again</div>
```

## Common uses

- Toast/snackbar notifications ("Saved", "Item added to cart")
- Form submission results, especially when the result doesn't cause a page navigation
- Live search result counts as a user types
- Loading-state announcements ("Loading more items…" / "12 more items loaded")

## The must-exist-before-changing gotcha

```html
<!-- Often silently missed by screen readers: the container and its
     final content both arrive in the same DOM update -->
<div aria-live="polite">3 new results found</div>
```

If this whole `<div>` is inserted fresh — attribute and text together — there's no "before" state for the screen reader to compare against, so no change event fires. The reliable pattern: render the live region empty (or with placeholder text) on initial mount, and update its text content in a later, separate render once real data arrives.

## Don't announce everything

A live region that fires on every minor state change trains users to ignore it, or actively interrupts them constantly if set to `assertive`. Reserve live regions for updates a sighted user would also naturally notice happened — not for every internal state transition.
