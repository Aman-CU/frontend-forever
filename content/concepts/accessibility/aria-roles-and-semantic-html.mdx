## Why semantic HTML comes first

Many HTML elements have an implicit ARIA role — `<button>` is `role="button"`, `<nav>` is `role="navigation"`, `<a href="...">` is `role="link"`. Screen readers build a separate **accessibility tree** from these roles, and it's that tree — not the visual layout — that determines what a screen reader user actually hears and can navigate by.

```html
<!-- Screen reader announces: "Submit, button" — for free -->
<button>Submit</button>

<!-- Screen reader announces: "Submit" — with no role at all -->
<!-- Also gets no keyboard support, no focus outline, nothing -->
<div onclick="submit()">Submit</div>
```

## Landmark elements

Landmarks let a screen reader user jump directly to a section of the page instead of reading through everything linearly:

- `<header>` — introductory content, usually top of page or a section
- `<nav>` — a block of navigation links
- `<main>` — the page's primary content (exactly one per page)
- `<aside>` — content tangentially related to the main content
- `<footer>` — closing content, usually page or section metadata

## Interactive elements are not interchangeable with styled divs

`<button>`, `<a>`, `<input>`, and `<select>` all ship with real keyboard support, a visible focus indicator, and a role a screen reader already understands — though the exact activation key varies by element: a button activates on both Enter and Space, a link only on Enter (Space scrolls the page instead), a checkbox toggles on Space. Recreating any of that on a `<div>` means manually rebuilding the correct behavior for the specific control being built — and it's easy to get wrong (a common bug: a `role="button"` div that responds to a mouse click but not to a keyboard Enter press).

## When you actually need ARIA

ARIA earns its place when no native element fully covers the pattern — either none exists at all (a tab panel), or the native option (like `<dialog>` for modals, or `<input type="range">` for a slider) doesn't give enough control over structure and styling for what's being built. In those cases:

```html
<div role="tablist">
  <button role="tab" aria-selected="true" id="tab-1">Profile</button>
  <button role="tab" aria-selected="false" id="tab-2">Settings</button>
</div>
```

Note that the tabs above are still real `<button>` elements underneath the ARIA role — ARIA augments semantics, it doesn't replace the need for a focusable, keyboard-operable base element.

## Three rules of thumb

1. **Prefer a native element over ARIA-on-a-div** whenever one exists for what you're building.
2. **Don't override native semantics unnecessarily** — putting `role="heading" aria-level="2"` on a `<div>` when you could just write `<h2>` adds complexity for zero benefit.
3. **Every custom ARIA widget must be fully keyboard-operable** to match the behavior its role implies — adding `role="button"` without also adding a `tabindex` and key handlers is worse than using no ARIA at all, because it promises behavior that isn't there.
