## Associating a label with its input

Two ways to create a real, programmatic association — not just visual proximity:

```html
<!-- for/id: label and input can be placed anywhere relative to each other -->
<label for="email">Email</label>
<input id="email" type="email" />

<!-- wrapping: no id needed, association is implicit -->
<label>
  Email
  <input type="email" />
</label>
```

Either way, a screen reader announces "Email, edit text" when the input receives focus, and clicking the label text focuses the input — neither happens with a `<span>` or `<div>` sitting visually near the input with no real association.

## Placeholder text is not a label

```html
<!-- Broken: no accessible name once the input is empty vs. focused,
     low default contrast, and disappears the moment text is typed -->
<input placeholder="Email" />
```

Placeholder text can supplement a label as a formatting hint ("MM/DD/YYYY"), but it should never be the only source of the field's name.

## aria-describedby for hints and errors

```html
<label for="password">Password</label>
<input
  id="password"
  type="password"
  aria-describedby="password-hint"
  aria-invalid="true"
/>
<p id="password-hint">Must be at least 8 characters</p>
```

The screen reader announces the label first ("Password"), then the field's state ("invalid"), then the referenced description text — all connected to the one field, all in one announcement.

## Grouping related inputs

A set of radio buttons or checkboxes describing one question benefits from `<fieldset>` + `<legend>`, so a screen reader announces the group's overall question once, rather than making the user infer it from repeated individual labels:

```html
<fieldset>
  <legend>Preferred contact method</legend>
  <label><input type="radio" name="contact" value="email" /> Email</label>
  <label><input type="radio" name="contact" value="phone" /> Phone</label>
</fieldset>
```

## Timing matters for validation announcements

Validating and announcing an error on every keystroke is overwhelming for screen reader users — the common pattern is to validate on blur (leaving the field) or on submit, not while the user is still mid-typing. How that announcement actually reaches the user without stealing focus is the next concept's job: ARIA live regions.
