## Why "apply edits in arrival order" corrupts the document

Two users both start from the same document text. User A inserts "X" at position 5. Concurrently, user B inserts "Y" at position 5 too — computed against the *original* text, before A's insert existed. If the server just applies both operations literally, in whatever order they arrive, one of them lands at the wrong position relative to the other's insert, and the two clients can end up with different final text — the definition of the documents diverging.

## Operational Transformation (OT)

OT's fix: before applying an incoming operation, transform its position against every operation that was concurrently applied ahead of it. If B's insert-at-5 arrives after A's insert-at-5 already landed, the server shifts B's position to 6 before applying it — both users converge on the same final text, with A's and B's characters both present in a well-defined order. This requires a central server to establish a single authoritative order operations get transformed against; it's the mechanism behind Google Docs' collaborative editing.

## CRDTs (Conflict-free Replicated Data Types)

CRDTs (Yjs, Automerge in practice) take a different approach: design the data structure so that operations commute by construction — applying the same set of operations in any order produces the same result, with no transformation step and no central server required to enforce an order. Text CRDTs typically give every character a unique, globally-ordered identifier (rather than a plain array index) — inserting "in between" two existing characters is well-defined regardless of what else got inserted concurrently, because positions are anchored to stable ids, not indices that shift.

## The rest of the system around either core

- **Transport** — WebSocket for live collaboration; an HTTP fallback or periodic snapshot sync for reconnection.
- **Persistence** — store the operation log (or CRDT update stream) plus periodic full-document snapshots, so loading a document doesn't require replaying its entire history from the start.
- **Presence** — cursor positions and selections are ephemeral, broadcast live but never written to the persisted op log or snapshot.
- **Scalability** — shard by document, and fan out operations to every connected client for that document via pub/sub (Redis, Kafka) rather than a single process holding every open document in memory.

## Why it matters

The interview signal isn't reciting "OT or CRDTs" as buzzwords — it's explaining *why* naive last-write-wins or apply-in-arrival-order breaks under concurrent edits, and only then which mechanism fixes it and what it costs (OT's central-ordering-server dependency vs. a CRDT's larger per-character metadata overhead).
