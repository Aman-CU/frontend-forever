## Three kinds of state, three different jobs

- **Server state** — data whose source of truth is a backend: a user's posts, a product catalog, an order status. It can change underneath the client (another user edited it, a background job updated it), so it needs staleness tracking and revalidation, not just storage.
- **UI state** — ephemeral, local to a specific interaction: is this dropdown open, what's currently typed in this unsubmitted field, which tab is selected. It doesn't need to survive a page refresh or be visible to unrelated parts of the app.
- **Global app state** — genuinely shared across the whole app, but small: the logged-in user, the active theme, feature flags. Its defining trait isn't "used in many places" — it's "there is exactly one source of truth for the whole session," unlike server state (many independent resources) or UI state (many independent, unrelated instances).

## Why mixing them causes the classic bugs

Putting server state in a plain global store is the most common mistake at scale: the store has no idea the underlying data can go stale, so either nothing ever refetches (a stale product price shown forever) or the team hand-rolls ad hoc refetch-on-mount logic in every component that needed it — reinventing exactly what a server-state library already solved once, correctly, in one place.

The opposite mistake — lifting UI state (a single dropdown's open/closed flag) into a shared global store — causes unrelated components to re-render whenever that flag changes, and makes state that should be trivially disposable outlive the component that owns it.

## Layering it correctly

- Server state → a dedicated library (React Query/SWR/Apollo) that owns fetching, caching, staleness, and invalidation.
- UI state → `useState`/`useReducer` scoped to the component (or its nearest shared ancestor) that actually needs it — not hoisted further than the components that read it.
- Global app state → a lightweight store (Context for rarely-changing values, or Zustand/Jotai for anything that changes more often) reserved for the genuinely session-wide handful of values, kept deliberately small.

## Why it matters

"Where should this piece of state live?" is really three separate questions bundled into one: is its source of truth the server (use the server-state library), is it local to one interaction (keep it local), or is it truly global (the smallest of the three categories, by far, in most real apps)? Skipping straight to "put it in the global store" for all three is what makes state management feel unmanageable as an app grows — not the amount of state itself.
