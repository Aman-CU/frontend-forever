## The cascade's real resolution order

When the browser has to choose one winning declaration for an element/property pair, it goes through these stages **in order**, only moving to the next when the current one ties:

1. **Origin & importance** — user-agent (browser default) styles lose to author (your CSS) styles, which lose to a user's own styles, and `!important` flips each of those pairs in reverse. A user's `!important` rule beats *everything*, including an author's `!important`.
2. **Specificity** — within the same origin/importance tier, the higher-scoring selector wins (see the CSS Specificity concept for the full `[id, class, element]` scoring).
3. **Source order** — if specificity also ties, the declaration that appears later in the stylesheet (or in a later-loaded stylesheet) wins.

This is why `!important` is so easy to misuse: it doesn't just raise specificity, it jumps to an entirely earlier stage of the cascade — which is also why the only clean way to override it is another `!important`, escalating a fight that specificity alone could never have caused.

## Inheritance

Separately from the cascade, some CSS properties automatically compute to the **same value as their parent** if nothing else sets them — no rule has to "win" anything for this to happen:

- **Inherited by default:** `color`, `font-family`, `font-size`, `line-height`, `visibility`, `list-style` — mostly text and typography properties, because it's rarely useful to reset every nested `<span>`'s font individually.
- **Not inherited by default:** `margin`, `padding`, `border`, `width`, `height`, `background` — box-model and layout properties, because a child having its own independent box is almost always what you want.

Any property can be forced either way with the `inherit` (take the parent's value) or `initial` (reset to the property's spec-defined default) keywords, regardless of whether it inherits naturally.

```css
.parent { color: navy; }
.child { /* color: navy — inherited, no rule needed */ }
.child--reset { color: initial; } /* explicitly opts out of inheritance */
```

## Why it matters

"Why is this text the wrong color" is almost always an inheritance question ("what did it compute to, with no matching rule?"), while "why did my rule not apply" is almost always a cascade question ("what beat it, and at which stage?"). Knowing which question you're actually asking cuts debugging time in half.
