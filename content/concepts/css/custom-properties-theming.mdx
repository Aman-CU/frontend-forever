## Declaring and reading a custom property

```css
:root {
  --accent-color: teal;
  --spacing-unit: 8px;
}

.button {
  background: var(--accent-color);
  padding: calc(var(--spacing-unit) * 2);
}
```

`var(--accent-color)` resolves at render time by looking up the cascade from the element using it — checking that element, then its ancestors, until it finds a matching `--accent-color` declaration (or falls back to the second `var()` argument, if provided: `var(--accent-color, blue)`).

## Runtime theming with scoped overrides

Because custom properties genuinely cascade, redefining one on a more specific ancestor overrides it for every descendant beneath that point — without touching the components' own CSS at all:

```css
.theme-dark {
  --accent-color: cyan;
  --surface-bg: #111;
}
```

Toggling a single class (`document.documentElement.classList.toggle("theme-dark")`) instantly reflows every component reading `--accent-color`, because the browser re-resolves the cascade for each one — no re-render, no JavaScript re-styling logic, no rebuild step.

## Why this can't be done with Sass/LESS variables

A preprocessor variable (`$accent-color`) is substituted with its literal value **before the browser ever receives the CSS** — by the time a stylesheet ships, every `$accent-color` reference has already been replaced with a fixed string. There's no runtime mechanism left to change it; doing so requires shipping an entirely new stylesheet (or a duplicate one per theme). Custom properties instead ship the *variable itself* to the browser, which is what makes live, JS-free theme switching possible in the first place.

## Why it matters

Runtime theming (dark mode, white-labeling, user-customizable accent colors) is one of the clearest places where "compiles to CSS" and "is CSS" stop being the same thing — and interviewers use this concept to check whether a candidate understands that distinction, not just that both syntaxes use a variable-looking token.
