## Local state: the default

```jsx
function SearchBox() {
  const [query, setQuery] = useState("");
  return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}
```

State that only one component (and its own children, via props) needs should stay exactly there. Reaching for Context or a global store before anything actually needs to share this value adds indirection with no benefit yet.

## Lifting state up

The moment a sibling component needs the same value, it moves to their nearest common ancestor, passed down as props to both:

```jsx
function SearchPage() {
  const [query, setQuery] = useState("");
  return (
    <>
      <SearchBox query={query} onQueryChange={setQuery} />
      <ResultsCount query={query} />
    </>
  );
}
```

This works cleanly for a couple of levels — it becomes prop drilling (the earlier concept in this path) once several layers of components in between don't use the value themselves.

## Context: broadcast, but all-or-nothing

Context solves the drilling problem but re-renders every consumer whenever the Provider's value changes, regardless of which part of it a given consumer reads — fine for state that changes rarely (theme, locale, the logged-in user), risky for state that changes often (a live cart total, real-time cursor positions).

## External stores: subscribe to a slice

```js
const useCartStore = create((set) => ({
  items: [],
  addItem: (item) => set((s) => ({ items: [...s.items, item] })),
}));

function CartCount() {
  const count = useCartStore((s) => s.items.length); // only re-renders when this changes
  return <span>{count}</span>;
}
```

A store paired with selectors (Zustand, Redux + `useSelector`, Jotai's atoms) lets `CartCount` subscribe to just `items.length` — a change to some other field in the store never re-renders it. This is the main advantage over Context at scale: re-render granularity down to the exact slice a component reads, not the whole Provider value.

## Why it matters

"Would you reach for Redux here?" is really asking whether you evaluate state's actual sharing radius and update frequency before picking a tool — not whether you can recite each library's API. Most real over-engineering in this area is introducing a global store for state that was never going to leave one component's subtree.
