## The prop drilling problem

```jsx
function App() {
  const [theme, setTheme] = useState("dark");
  return <Layout theme={theme} />;
}
function Layout({ theme }) {
  return <Sidebar theme={theme} />; // Layout never uses theme itself
}
function Sidebar({ theme }) {
  return <ThemeToggle theme={theme} />; // Sidebar never uses theme itself
}
```

`Layout` and `Sidebar` only exist to forward `theme` — adding a new prop, renaming one, or inserting a component in the middle means touching every intermediate layer even though none of them care about the value.

## Context: publish once, read anywhere

```jsx
const ThemeContext = createContext("light");

function App() {
  const [theme, setTheme] = useState("dark");
  return (
    <ThemeContext.Provider value={theme}>
      <Layout />
    </ThemeContext.Provider>
  );
}
function Layout() { return <Sidebar />; }
function Sidebar() { return <ThemeToggle />; }
function ThemeToggle() {
  const theme = useContext(ThemeContext); // reads directly, no props passed through
  return <button>{theme}</button>;
}
```

`Layout` and `Sidebar` no longer mention `theme` at all — only the component that actually needs it calls `useContext`.

## The re-render tradeoff

Every component that calls `useContext(ThemeContext)` re-renders whenever the Provider's `value` changes — regardless of which part of that value it actually reads. A context holding `{ theme, user, cart }` causes every consumer to re-render on a cart update, even a component that only reads `theme`. This is why large apps often split one big context into several narrow ones, or pair Context with `useMemo` on the provided value.

## Why it matters

Context is the right tool for values that are genuinely global to a subtree — theme, locale, the current authenticated user — not a general replacement for passing props. Reaching for Context to avoid drilling two levels deep usually adds more indirection than it removes.
