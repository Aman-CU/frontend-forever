## Template literal types

A template literal type describes every string matching a pattern, built the same way a template literal string is built:

```ts
type EventName = `on${Capitalize<string>}`;
// matches: "onClick", "onSubmit", "onChange" — not "click" or "onclick"

type CSSVariable = `--${string}`;
// matches: "--primary-color", "--gap" — not "primary-color"
```

Combined with a union, template literal types can enumerate every valid combination at compile time:

```ts
type Direction = "top" | "right" | "bottom" | "left";
type Margin = `margin-${Direction}`;
// "margin-top" | "margin-right" | "margin-bottom" | "margin-left"
```

`Margin` isn't just typed as `string` — it's exactly those four literal strings, so `margin: "margin-diagonal"` is a compile error, not a typo waiting to be caught in code review.

## The structural typing problem branded types solve

TypeScript compares types by shape, not by name — two type aliases with an identical underlying shape are fully interchangeable:

```ts
type UserId = string;
type OrderId = string;

function getUser(id: UserId) { /* ... */ }
const orderId: OrderId = "order_123";
getUser(orderId); // compiles — both are just `string` under the hood
```

This is exactly the bug a type system should catch — passing an order ID where a user ID belongs — and structural typing lets it through, because to the compiler `UserId` and `OrderId` are both simply `string`.

## Branded types

A brand adds a compile-time-only marker property that makes two otherwise-identical shapes incompatible:

```ts
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };

function makeUserId(raw: string): UserId {
  return raw as UserId; // the one place the brand is asserted
}

function getUser(id: UserId) { /* ... */ }

const orderId = "order_123" as OrderId;
getUser(orderId); // compile error — OrderId is not assignable to UserId
```

`__brand` never actually exists at runtime — no real string has that property — it's a type-only fiction whose sole purpose is to make the compiler refuse to treat `UserId` and `OrderId` as the same type, even though both compile down to a plain `string`.

## Why it matters

Template literal types catch malformed string patterns — event names, CSS variables, route paths — before the code runs at all. Branded types close the gap structural typing otherwise leaves open for "same shape, different meaning" values like IDs, currency amounts, or units — the two most common real-world uses for a technique that otherwise looks like a party trick.
