## The four options

| | Capacity | Lifetime | Sent to server? |
|---|---|---|---|
| **Cookies** | ~4KB per cookie | set via `Expires`/`Max-Age`, or session-only | yes, automatically, on every matching request |
| **sessionStorage** | ~5-10MB | until the tab closes | no |
| **localStorage** | ~5-10MB | forever, until explicitly cleared | no |
| **IndexedDB** | hundreds of MB+ (browser-dependent) | forever, until explicitly cleared | no |

```js
localStorage.setItem("theme", "dark"); // persists across tabs and browser restarts
sessionStorage.setItem("draftId", "42"); // gone when this tab closes
document.cookie = "session=abc123; Max-Age=3600; Secure; SameSite=Strict";
```

## Why cookies are different

Cookies are the only mechanism here that the **server** can read without any extra JavaScript — the browser attaches every cookie matching the request's domain/path automatically. That's exactly why auth sessions traditionally use cookies (the server needs to see them) and exactly why a bloated cookie is a real performance problem: every cookie byte is sent on *every single request* to that domain, including images and stylesheets.

`localStorage`/`sessionStorage`/IndexedDB are the opposite — invisible to the server unless your JavaScript explicitly reads and sends them.

## When each is the right tool

- **Cookies** — anything the server needs on every request: session tokens, auth state. Keep them small.
- **sessionStorage** — per-tab, ephemeral state that shouldn't survive a reload elsewhere: a multi-step form's in-progress values, a "don't ask again this session" flag.
- **localStorage** — small settings that should persist indefinitely: theme preference, a dismissed-banner flag. Synchronous API — reading a large value blocks the main thread, which is why it's wrong for anything beyond simple key/value settings.
- **IndexedDB** — structured or large data: offline caches, a local copy of a user's documents, anything measured in megabytes. Asynchronous by design, so it never blocks rendering the way `localStorage` can.

## Why it matters

The most common real-world mistake is reaching for `localStorage` to store a large JSON blob "because it's easy" — it's synchronous, so a multi-megabyte read/write can visibly jank the page, and it silently fails once you're near the quota. Anything beyond small settings belongs in IndexedDB (usually through a wrapper library), not `localStorage`.
