## An origin is scheme + host + port

Two URLs are the "same origin" only if their protocol, hostname, and port all match exactly:

```
https://app.example.com:443  vs  http://app.example.com:443   → different (scheme)
https://app.example.com      vs  https://api.example.com      → different (host)
https://app.example.com:443  vs  https://app.example.com:8080 → different (port)
```

Without CORS, JavaScript on `https://app.example.com` cannot read a response from `https://api.example.com` — even though the request itself is sent, the browser blocks the calling script from accessing the response body.

## Simple requests vs. preflight

A **simple request** (`GET`/`HEAD`/`POST` with only a small set of allowed headers/content-types) is sent directly, and the browser just checks the response's `Access-Control-Allow-Origin` header before deciding whether to expose it to JavaScript.

Anything else — a custom header like `Authorization`, a method like `PUT`/`DELETE`, or `Content-Type: application/json` on some setups — triggers a **preflight**: the browser sends an `OPTIONS` request *first*, asking the server "would you allow this actual request?" before sending the real one.

```
OPTIONS /api/data
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

← 204 No Content
  Access-Control-Allow-Origin: https://app.example.com
  Access-Control-Allow-Methods: GET, PUT
  Access-Control-Allow-Headers: Content-Type, Authorization
```

Only if the preflight response allows the method and headers does the browser send the real `PUT` request.

## The response headers that matter

- `Access-Control-Allow-Origin` — which origin(s) may read the response (`*` or a specific origin)
- `Access-Control-Allow-Methods` — which HTTP methods are allowed cross-origin
- `Access-Control-Allow-Headers` — which request headers are allowed
- `Access-Control-Allow-Credentials` — whether cookies/auth headers can be included; requires an exact origin, never `*`

## Why it matters

CORS errors are one of the most common frontend/backend integration bugs, and the fix is always server-side — a frontend developer can't "work around" a CORS error by changing client code, because the browser is the one enforcing it. Understanding that the request already reached the server (visible in server logs) even when the browser shows a CORS error in the console is the key to not wasting time debugging the wrong side of the request.
