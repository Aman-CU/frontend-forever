## The six stages

1. **DOM** — the browser parses HTML into a tree of nodes representing content and structure.
2. **CSSOM** — the browser parses CSS into a tree representing every style rule and how it cascades.
3. **Render Tree** — DOM + CSSOM combine into a tree containing only the nodes that will actually be visible, each carrying its final computed styles. `display: none` elements are dropped entirely here.
4. **Layout (reflow)** — the browser computes the exact geometry (position, size) of every node in the render tree.
5. **Paint** — the browser fills in pixels: colors, borders, shadows, text — for every node, but not yet combined into a final image.
6. **Composite** — separately painted layers are combined in the right stacking order into what actually appears on screen.

```
HTML ──▶ DOM ─┐
              ├──▶ Render Tree ──▶ Layout ──▶ Paint ──▶ Composite
CSS ───▶ CSSOM ┘
```

## Why some changes are cheaper than others

The pipeline doesn't always restart from the top — the browser only re-runs the stages a change actually affects:

- **Layout-triggering properties** (`width`, `top`, `margin`, `font-size`) — force Layout → Paint → Composite, because changing one element's geometry can cascade to its siblings and ancestors.
- **Paint-only properties** (`color`, `background`, `box-shadow` on a non-positioned element) — skip Layout, but still trigger Paint → Composite.
- **Composite-only properties** (`transform`, `opacity`) — skip both Layout and Paint. The GPU can reuse the already-painted layer and just reposition/fade it.

This is exactly why animating `transform: translateX()` is smooth while animating `left` on the same element is not — one only touches Composite, the other re-triggers the whole pipeline on every frame.

## Render-blocking resources

CSS is render-blocking by default: the browser won't build the Render Tree — and therefore won't paint anything — until the CSSOM is ready, to avoid a flash of unstyled content. A synchronous `<script>` (no `async`/`defer`) is parser-blocking on top of that: it halts HTML parsing itself until the script downloads and executes, delaying when the DOM is even complete.

## Why it matters

Every "why is my animation janky" question traces back to this pipeline. The fix is almost always the same: stop animating layout- or paint-triggering properties and animate `transform`/`opacity` instead, letting the browser skip straight to Composite on every frame.
