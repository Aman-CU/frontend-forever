## Intercepting requests

A registered service worker listens for every request the page makes:

```js
self.addEventListener("fetch", (event) => {
  event.respondWith(handleRequest(event.request));
});
```

`event.respondWith()` lets the service worker fully control what response the page receives — from an actual network fetch, from a pre-populated `Cache` object, or a mix of both. This interception is also what makes offline support possible: if the network fetch fails, the service worker can fall back to whatever's cached instead of the page showing a browser error.

## Three caching strategies

**Cache-first** — check the cache; only hit the network on a miss. Best for assets that rarely change (versioned JS/CSS bundles, fonts, icons):

```js
async function cacheFirst(request) {
  const cached = await caches.match(request);
  if (cached) return cached;
  const response = await fetch(request);
  const cache = await caches.open("v1");
  cache.put(request, response.clone());
  return response;
}
```

**Network-first** — always try the network; fall back to cache only if the network fails. Best for data that must be fresh whenever possible (a live feed, account balance):

```js
async function networkFirst(request) {
  try {
    const response = await fetch(request);
    const cache = await caches.open("v1");
    cache.put(request, response.clone());
    return response;
  } catch {
    const cached = await caches.match(request);
    if (cached) return cached;
    throw new Error("No network and no cache available");
  }
}
```

**Stale-while-revalidate** — respond from cache immediately (fast, possibly stale), then fetch from the network in the background to update the cache for next time. Best for content that changes occasionally but shouldn't block the current view (a news list, a settings page):

```js
async function staleWhileRevalidate(request) {
  const cache = await caches.open("v1");
  const cached = await cache.match(request);
  const networkFetch = fetch(request).then((response) => {
    cache.put(request, response.clone());
    return response;
  });
  return cached || networkFetch;
}
```

## Why it matters

Choosing the wrong strategy causes real user-facing bugs: cache-first on an API that returns live data means users see stale numbers indefinitely; network-first on a large static bundle means every load is blocked on a network round trip that was entirely avoidable. The strategy should be chosen resource-by-resource, not applied uniformly to every request a service worker intercepts.
