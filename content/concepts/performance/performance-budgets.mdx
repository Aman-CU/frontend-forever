## Why performance regresses gradually, not suddenly

No single PR usually looks like "let's make the app noticeably slower." It's a 12kb icon library added for one icon, a slightly heavier date-formatting dependency, an image that wasn't quite optimized — each individually invisible, cumulatively real. Without an enforced ceiling, there's no single point where any of these gets blocked.

## What gets budgeted

Common budget targets: total JS bundle size (often broken down per route), image payload weight, and the Core Web Vitals scores themselves (LCP, INP, CLS) measured against a fixed threshold. Bundle size budgets are the easiest to enforce mechanically, since they're computed at build time with no real-user variability involved.

## Enforcing it in CI

A budget check runs on every PR: build the app, measure the relevant metric, compare it against the budget, and fail the build if the metric exceeds it — exactly like a failing test blocks merge. Tools like `bundlesize`, Lighthouse CI, or a custom build-time script all follow the same shape: measure, compare, gate.

## Budgets vs. baselines

A pure fixed budget ("bundle must stay under 200kb") is simple but can miss a smaller, still-meaningful regression if the app started well under budget with room to spare. Comparing against the *previous* build's baseline — not just the fixed ceiling — catches "this PR alone grew the bundle by 15%" even when the absolute number hasn't crossed the budget line yet, which is often the more actionable signal for the specific PR under review.

## Budgets need owners, not just numbers

A budget that fails builds with no clear next step just gets bypassed under deadline pressure. The teams that keep budgets effective pair every budget with an obvious action when it's exceeded — split this chunk, defer this dependency, revisit this image — so failing the check is a solvable problem, not a blocker someone has to argue their way around.
