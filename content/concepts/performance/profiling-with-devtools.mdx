## Reading a flame chart

Each horizontal bar represents one function call. Width = duration. Bars stacked below a bar are the functions it called. Scrolling and zooming through a real recording, the first instinct is often to chase the *widest* bar — but the widest bar is frequently just a high-level function (a render, an event handler) whose width is mostly its children's time, not its own.

## Self time vs. total time

- **Total time**: this function's duration, including every function it called.
- **Self time**: this function's duration, *excluding* time spent inside anything it called — i.e., the work it actually did itself.

A function that calls three slow helpers and does almost nothing else will show large total time but small self time. The helper that's actually slow is the one to fix — and it's identified by self time, not by which bar looks widest on screen.

## The Bottom-Up view

Because the same function can appear in many different call stacks across a recording (a `formatCurrency` helper called from a dozen different components, for instance), looking at any single flame chart node can undercount its real cost. DevTools' **Bottom-Up** tab aggregates self time for a function across every place it was called during the whole recording — surfacing "this function cost 400ms in total, spread across 200 tiny calls" even when no single call stack shows it as the obvious bottleneck.

## React DevTools Profiler

The generic Performance panel has no idea what a "component" is — it just sees function calls. React DevTools' own Profiler adds that layer back: it records a commit, shows which components rendered during it, and estimates how long each took, making it much faster to spot "this component re-rendered on every keystroke even though its props didn't change" than digging through a raw flame chart for the same insight.

## The actual workflow

1. Record a real interaction (not a synthetic guess at what's slow).
2. In the flame chart or Bottom-Up view, sort by self time, not total time.
3. Fix the highest self-time function first — it's the one with the best chance of being the genuine bottleneck, not just a slow wrapper around something else.
