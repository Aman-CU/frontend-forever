## The three metrics

| Metric | What it measures | Good | Poor |
|---|---|---|---|
| LCP (Largest Contentful Paint) | Time until the biggest visible element renders | ≤ 2.5s | > 4.0s |
| INP (Interaction to Next Paint) | Delay between an interaction and the next visual update | ≤ 200ms | > 500ms |
| CLS (Cumulative Layout Shift) | Sum of unexpected layout shift scores during the page's lifetime | ≤ 0.1 | > 0.25 |

Values strictly between "good" and "poor" fall into a middle "needs improvement" bucket.

## LCP: what usually causes it to be slow

The largest element is often a hero image, a background image applied via CSS, or a large block of text. Common LCP killers: the image isn't preloaded so the browser discovers it late; render-blocking CSS/JS delays the whole page's first paint; the server itself is slow to respond with the initial HTML.

## INP: replacing First Input Delay

INP superseded an older metric (First Input Delay) because FID only measured the delay before an interaction *started* processing — INP measures the entire round trip from interaction to the next paint, across every interaction during the visit, not just the very first one. A page that feels fine on the first click but janky on the fifth now gets penalized correctly.

## CLS: why it's cumulative, not just "did something move"

CLS sums up every unexpected shift's score across the whole page lifetime, not just the worst single jump. An image with no reserved `width`/`height`, a web font that swaps in and reflows text, or an ad slot that loads late and pushes content down are the most common causes — all fixed the same way: reserve the space up front before the content that will fill it has actually loaded.

## Why "real user" measurement, not a lab test

A lab test (like a single Lighthouse run) measures one simulated device on one simulated network. Core Web Vitals instead come from the Chrome User Experience Report — aggregated data from real Chrome users visiting the page — which is why the 75th-percentile rule matters: it has to hold up across a real, messy distribution of devices and networks, not just the reviewer's own laptop.
