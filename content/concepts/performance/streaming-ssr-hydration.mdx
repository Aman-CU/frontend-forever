## The problem streaming solves

Without streaming, a page with one slow data dependency (a personalized recommendations widget, a slow third-party API call) delays the *entire* response — the fast, static parts of the page (header, nav, most of the layout) wait on the single slowest piece even though they had nothing left to do.

## Suspense boundaries as the unit of streaming

A `<Suspense>` boundary marks a section of the tree that's allowed to "not be ready yet." The server sends the shell immediately with a fallback in that boundary's place, then streams the real content in — replacing the fallback — the moment that boundary's data resolves. Multiple boundaries can resolve and stream in whatever order their own data finishes, independent of each other and independent of their document position.

## Why arrival order doesn't determine final order

Each streamed chunk is tagged with the id of the placeholder it belongs to. The browser doesn't append streamed content to the end of the page — it slots each chunk into its already-reserved position. A footer that finishes fast still ends up in the footer, even if it streamed in before the (slower) main content did.

## Hydration: attaching behavior to markup that already exists

Once HTML has streamed in — from the server, already visible as static markup — hydration is React walking that same tree on the client, matching it up node-for-node with what the client-side render would have produced, and attaching real event handlers and internal state without throwing away and rebuilding the DOM. This is why SSR content is visible before it's *interactive*: paint happens first, hydration happens after (and streaming lets each piece hydrate as its own chunk arrives, rather than waiting for the whole page).

## Hydration mismatches

If the server-rendered markup and what the client expects to hydrate don't actually match — different text, different element, different order — React can't just silently reconcile it the way a normal re-render would; it has to detect the mismatch and recover (typically by discarding the mismatched section and re-rendering it client-side), which is slower and can cause a visible flash. Common causes: rendering something that depends on `Date.now()` or `Math.random()` differently on server vs. client, or reading browser-only globals (`window`, `localStorage`) during the server render.
