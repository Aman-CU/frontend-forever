## The problem: one bundle for every route

Without splitting, every route's code — and every dependency each route pulls in — lands in a single file the browser must download and parse before anything on the page can run, even routes the user never visits in that session.

## Route-based splitting

Most modern frameworks split automatically at the route boundary: visiting `/login` only downloads the login route's chunk, not `/checkout`'s or `/admin`'s. In Next.js's App Router, this happens per-page by default — each route segment becomes its own chunk without extra configuration.

## Shared chunks: the modules multiple routes actually use

If `/login`, `/checkout`, and `/admin` all import React and a shared `Button` component, the bundler pulls those into one shared chunk instead of duplicating them into all three route chunks. The rule that decides this is purely about usage count: a module used by more than one entry point graduates to shared; a module used by exactly one stays local to it.

## Component-level splitting with dynamic import

Splitting isn't only per-route — a single heavy component (a rich text editor, a charting library, a modal that's rarely opened) can be split out on its own with a dynamic import, so its cost is only paid when that component actually renders:

```js
const HeavyEditor = dynamic(() => import("./HeavyEditor"));
```

This is the same underlying mechanism as route splitting, just triggered by a component boundary instead of a route boundary.

## Measuring what's bloating the bundle

A bundle analyzer visualizes each chunk as a proportionally-sized box, making it easy to spot a single oversized dependency (a full date library pulled in for one formatting call, an icon set imported in full instead of per-icon) that's worth splitting out or replacing with a lighter alternative.
